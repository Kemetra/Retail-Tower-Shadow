# kemetra-agent token broker: design (RT-721 Substep B, step B6)

**Status: built, not yet run against GitHub.** The broker is `tools/agent-broker/broker.py`, with the wrapper `Start-KemetraAgentSession.ps1` and 19 tests that use a throwaway key. The owner generated the App key into 1Password (vault `tower`, item `kemetra agent bot`) on 2026-10-19. The first real run is done by the owner. Changing credential stores (L2) needs its own authorization.

## Usage (owner)

1. **Dry run:**

   ```powershell
   .\tools\agent-broker\Start-KemetraAgentSession.ps1 -Check
   ```

   1Password asks you to unlock. The script mints a token, checks it covers only the Shadow with the 6 grants, revokes it, and prints only the expiry, the repo and the permissions.
   - If the 1Password field isn't called `private key`, pass the exact reference: `-OpRef 'op://tower/kemetra agent bot/<field>'`. If the key is stored as an attached file, the field is the file's name.
2. **Session:** run `.\tools\agent-broker\Start-KemetraAgentSession.ps1` (starts `claude`). Use `-Command pwsh` instead for a plain shell. The token is revoked when the command exits, and it expires after 1 hour either way.
3. Inside the first session, have the agent run acceptance checks A1–A7 below.

## Goal

Agent sessions working on `Kemetra/Retail-Tower-Shadow` act as **`kemetra-agent[bot]`**, never as the owner account `Kemetra`. This closes F2 (RT-721 comment 12997) and makes the A.8 R1 split real: a human `Kemetra` action can then only come from the owner.

The broker must meet four constraints:

- The agent **never sees the App private key**. It is generated by the owner, kept only in 1Password, and read only in the owner's shell.
- The agent receives only a **1-hour installation token**, scoped to one repository (`repository_ids: [1425468661]`) and to the App's grants or fewer.
- **No workflows permission:** this only stops the agent changing `.github/workflows/**`. It does **not** protect the other policy-class paths. With `contents:write`, the bot can push straight to an unprotected `main` and rewrite:
  - `tools/project-graph/**`, the trusted evaluator and aggregator the gate checks out as base;
  - `graph.yaml`, including `policy_approvers`;
  - `tools/ci-gate/**`, `CODEOWNERS`, or a future `.github/actions/*`.

  Shadow `main` has **0 rules today**: the B4 ruleset covers only `canary/**`. Protecting these paths needs the **`main` ruleset prerequisite** below.
- The owner credential is **not reachable** from the agent session (see "Separation").

## Prerequisite: `main` ruleset before the broker goes live (its own owner gate)

Before the bot holds any token, add a `main` ruleset with these settings:
- pull request required, with **1 approval**;
- **require approval of the most recent push**;
- no force push and no deletion;
- bypass limited to the **repository admin** role, which the owner holds and the bot does not.

It does **not** require the `required` check yet, so it doesn't conflict with B8: `main` is not blocked by a gate that can't pass. The bot can then change policy paths only through a PR that the owner approves.

**Needs verification:** whether ruleset PR-approval rules are enforced on a private Pro repo. Pro rejected environment reviewers in B2. A small canary on a branch pattern, like B4, answers this before relying on it.

## Owner-only setup (before the broker is built)

1. In the App settings, generate a private key for `kemetra-agent`.
2. Store the full PEM in 1Password, for example item `kemetra-agent GitHub App`, field `private_key`, in a vault the owner chooses.
3. Delete the downloaded `.pem`.
4. Record only the `op://` reference, which is not secret, for the broker config.

## Flow (one session)

```
owner shell                                   GitHub
-----------                                   ------
Start-KemetraAgentSession.ps1
  op read op://<vault>/kemetra-agent/private_key   (1Password unlock prompt = owner approval)
  -> key kept in a process variable only, piped on stdin
  mint-app-jwt (python, cryptography/PyJWT):
     RS256, iss=5373224, iat=now-60, exp=now+540
  POST /app/installations/173158171/access_tokens
     {"repository_ids":[1425468661], "permissions":{...6 grants above...}}
  <- {token: ghs_..., expires_at: +1h}
  key variable cleared
  start agent process with ONLY:
     GH_TOKEN=<ghs token>          (gh uses it over any keyring entry)
     GH_CONFIG_DIR=<empty dir>     (no owner hosts.yml)
     GIT_CONFIG_* -> credential.helper reset; helper returns GH_TOKEN for github.com
     GIT_AUTHOR/COMMITTER = kemetra-agent[bot] identity
     working dir = the Shadow checkout
```

When the token expires after 1 hour, the owner runs the script again. Early revocation is `DELETE /installation/token` with that token, or deleting the App key.

## Separation: how far the owner credential is kept away

Today the machine's `gh` keyring holds a token that authenticates as **`Kemetra`** (admin). Git Credential Manager likely holds one too. An environment override (above) makes the agent *use* the bot token, but a process running as the same Windows user could still *read* those stores. Three levels:

| Level | What | Assurance | Cost |
| --- | --- | --- | --- |
| L1 | Env override only (flow above) | Agent uses the bot by default; owner token still reachable if a session misbehaves | lowest |
| L2 | L1 **plus** the owner removes the `Kemetra` token from `gh` and Git Credential Manager on this Windows profile, and does owner GitHub actions only in the browser | No owner token on disk for this user; the agent can only hold the 1-hour bot token | medium |
| L3 | Agent sessions run under a **separate Windows user** (or VM/container) that never holds owner credentials; the broker hands the token to that profile | Hard OS boundary | highest |

**Recommendation: L2 now, L3 before relying on R1 at gate activation (B8).** Only L2 or above lets `Kemetra` later go into `policy_approvers` as "human only".

**L2 consequence:** with no `Kemetra` token on this profile, nothing on this machine can do **admin** writes any more, and the bot is not an admin. These become owner actions in the browser:
- rulesets (including the `main` prerequisite and cleanup of canary ruleset 25431123);
- environments;
- B7 and B8.

**Until the broker is live, every agent write is an owner-account action.** That covers every Shadow write so far: the RT-710 import, the Substep A merge, B2–B4, and any further write from the current desktop session.

**Desktop app note:** Claude desktop sessions inherit the environment of the app process, so a per-session `GH_TOKEN` is not available there. Under L1 or L2, broker-scoped sessions use the `claude` CLI launched from the broker shell. Desktop sessions must not be used for Shadow writes, or must run under L3.

## Acceptance checks (B6 verification; RT-711 witnesses independently)

| # | Check | Expected |
| --- | --- | --- |
| A1 | Inside a broker session: `gh api /installation/repositories` | exactly `Kemetra/Retail-Tower-Shadow` |
| A2 | Push a test branch and open a PR on the Shadow | identity recorded **by GitHub**: the push event's `pusher` and the PR's `user.login` are `kemetra-agent[bot]` (344537132), not `Kemetra`. Git author and committer are set from env vars and prove nothing |
| A3 | Push a change under `.github/workflows/` | **refused** (no workflows permission) |
| A3b | Push a change to `tools/project-graph/graph.yaml` **directly to `main`** | **refused** by the `main` ruleset. Without the prerequisite ruleset this would succeed, which is the evidence for the gap |
| A4 | Write to any other repo (e.g. `Kemetra/POS`) | **refused** |
| A5 | Use the token after 1 hour | 401 |
| A6 | In the session: look for the owner token (env, `GH_CONFIG_DIR`, git credential helper) | none (L2); at L1, record as residual |
| A7 | Broker logs and the session transcript | no key material; no token value printed |

## Build plan (each item needs owner authorization)

1. **Owner** (key, as above).
2. **Owner-gated:** the `main` ruleset prerequisite, plus its approval-rule canary on a branch pattern.
3. **Agent** writes, test-first, in `tools/agent-broker/`:
   - `Start-KemetraAgentSession.ps1`;
   - `mint_token.py` (JWT, then installation token; the key is read from stdin only, and the token is never printed);
   - unit tests with a throwaway test key generated inside the test, never the real one.
4. **Owner** runs the broker for the first time, and the agent then runs A1–A7, including A3b.
5. **Owner** does L2 cleanup of the `Kemetra` token stores on this profile.
6. Record on RT-721. RT-711 independently re-checks A2–A5.

## Rotation and revocation

- **Key rotation:** every 90 days, or immediately on suspicion (RT-720 §7). The new PEM goes into 1Password and the old key is deleted in the App settings.
- **Containment:** suspend or uninstall installation 173158171. Any token still outstanding dies within 1 hour.
